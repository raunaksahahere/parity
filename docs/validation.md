# Validation study

This document reports how well Parity detects known faults and how often it wrongly flags
correct deployments. **Every number in the tables comes from `parity inject-faults run`** (raw
per-repetition data: [data/validation-results.jsonl](data/validation-results.jsonl), and for the
first run [data/validation-v1-results.jsonl](data/validation-v1-results.jsonl)); the tables are
generated by `scripts/update_result_docs.py`, not typed.

The study was run twice. The first run exposed a sampler-probe misattribution (see
[the appendix](#appendix-first-run-sampler-probe-v1)); the probe was fixed (v2) and the whole study was
re-run with the same calibration. The **Results** section is the second run. Reproduce with
`parity inject-faults run --out runs/validation` (resumable) and
`parity inject-faults summarize --out runs/validation`.

## Setup

| | |
|---|---|
| Hardware | AMD Ryzen 5 5600H (12 threads), 7.1 GB RAM, AMD RX 6500M 4 GB (Vulkan), no CUDA |
| Software | Python 3.12.3, torch 2.15.0+cpu, transformers 5.22.1, llama.cpp b12128 (prebuilt Vulkan and CPU) |
| Model | Qwen3-0.6B |
| Reference | `Qwen/Qwen3-0.6B` at revision `c1899de289a04d12100db370d81485cdf75e47ca`, HF transformers, fp32, CPU |
| Targets | llama.cpp GGUFs built by `llama-quantize` from one BF16 file (`unsloth/Qwen3-0.6B-GGUF@50968a4`) |
| Suite | `core` (all six probes), `core-v1` data, familywise alpha 0.05, claimed context 4096 |
| Machine load | A single user's laptop. Light editing, a few short test runs and one low-priority (`nice 19`) Docker image build happened while the study ran, so the wall-clock figures are "laptop under light concurrent use", not an isolated benchmark |

**Prompt cache.** In the second run, the CPU control and eight fault scenarios ran with
llama.cpp's default 8 GiB host prompt cache; it drove the machine into swap, so the remaining
scenarios (both GPU controls and the three quantizations) ran with `--cache-ram 0`
(decision D12). Each scenario uses one setting throughout. The second run was also
interrupted once by a machine reboot (after repetition 4 of `control-gpu-p1-smallbatch`) and
resumed with `parity inject-faults run`, which skips finished repetitions; the remaining
repetitions of that control used a fresh server process with the same configuration.

**Backends.** GPU deployments run on the RX 6500M through Vulkan (the server log line
`offloaded 29/29 layers to GPU` is asserted at start-up); CPU deployments use the CPU build.

### Calibration (benign deployments only)

Thresholds were calibrated *only* on two correct deployments that differ in benign ways:
`benign-gpu-p4` (BF16, GPU, 4 slots) and `benign-cpu-p4` (BF16, CPU, 4 slots). Resulting
thresholds ([data/validation-calibration.json](data/validation-calibration.json)):

| metric | benign-gpu-p4 | benign-cpu-p4 | threshold (max x 2) |
|---|---:|---:|---:|
| mean KL lower bound (nats, upper CI) | 6.75e-06 | 6.78e-05 | 1.36e-04 |
| greedy divergence hazard (Wilson upper) | 0.00474 | 0.00788 | 0.0158 |
| tool-trigger disagreement (Wilson upper, 0/24) | 0.138 | 0.138 | 0.276 |

### Controls (held out from calibration)

Correct deployments configured *differently* from the benign ones, so the false-positive rate
is measured on configurations the thresholds never saw. Each repetition is a full `core` run
with a different seed.

| control | configuration | repetitions |
|---|---|---:|
| `control-gpu-p2` | BF16, GPU, 2 slots, ctx 8192 | 10 |
| `control-gpu-p1-smallbatch` | BF16, GPU, 1 slot, `-b 128 -ub 64` | 10 |
| `control-cpu-p1-t4` | BF16, CPU, 1 slot, 4 threads | 3 |

### Injected faults (3 repetitions each)

| fault | how it is produced |
|---|---|
| `template-llama3` | real: `--chat-template llama3` |
| `template-nosystem` | real: custom template file without a system role (llama.cpp polyfills the system text into the user turn) |
| `quant-q8_0`, `quant-q4_k_m`, `quant-q2_k` | real: GGUF quantizations of the same BF16 weights |
| `ctx-reduced` | real: `--ctx-size 2048`, one slot, while 4096 is "claimed" |
| `topk-ignored`, `topp-ignored`, `temperature-ignored`, `temperature-x1.5` | **simulated**: a proxy rewrites the request fields before they reach an otherwise correct server (llama.cpp has no switch for these bugs) |
| `silent-truncation` | **simulated**: a proxy keeps only the last 6000 characters of the final user message |

## Appendix: first run (sampler probe v1)

Same calibration, scenarios and repetitions, run with sampler probe v1. In one of three Q2_K
repetitions the sampler probe reported a deviation for `top_p=0.6` (2.4% of samples outside the
nucleus). The sampler itself was correct: the server's own log-probs jitter slightly between
requests, and that context's cumulative mass sat within a hair of 0.6, so the boundary token
moved in and out of the nucleus. The overall verdict was still a correct DEVIATION (the
distributional and greedy probes caught the quantization), but the *attribution* was wrong.
v2 places `top_p` per context away from cumulative-mass boundaries (decision D11); a regression
test reproduces the situation.

## Limits of this study

* One small model, one reference, one serving stack (llama.cpp). Nothing here says how the
  probes behave on a 70B model, on vLLM or on a hosted provider; those adapters are
  implemented against documented formats and fixture-tested, not validated live.
* Faults marked *simulated* are bugs injected by a request-rewriting proxy; real servers that
  have those bugs could differ in detail.
* Repetitions of one deployment share the same server process and the same reference results;
  they are independent in the sampler's randomness and in the seed, not in the deployment.
* Controls give a confidence interval, not a guarantee: with N runs and zero false positives the
  upper 95% bound on the false-positive rate is about 3/N.
